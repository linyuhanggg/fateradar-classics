# 救应标签审计：`rescue: unimplemented` 到底有多少条真的「有救应可实现」（2026-09-12）

## 为什么要审

`references/executable/*.json` 里 258 条定义中 **212 条**标着 `rescue: "unimplemented"`（占 82%）。
按 `schema.md` 的字面含义，这个值读作「原文有救应条款、引擎尚未实现」——即一张 212 条的待实现清单。
但 82% 这个比例本身就值得怀疑：它更可能是把「原文根本没有救应条款」也写成了同一个值。
两者混在一起，会**虚增未决清单**：读的人会以为有 212 条救应有待实现。

## 怎么审的（方法）

1. 从 212 条里取 **108 条**做分层抽样：关键词（救／解／制／化）命中组全部取（73 条）+ 非命中组等距取 35 条。
2. 每条取出该条**自己的原文**（`sources[].quote`）与 fulltext 中该段前后各 6 行的上下文，交给 8 个独立校核员阅读。
3. 判据是**该条原文自己的话**，不是关键词：`制／化` 出现在一般用神叙述（如「以丙火制庚金」）不算救应；
   不含这些字但语义是「出了毛病另有物可救／使其不为害／反成」的**要算**。
4. 三选一：`has_rescue`（原文确有救应条款，并给出逐字引文）／`no_rescue`（原文只讲成立条件）／`unclear`。
   不确定写 `unclear`，不猜；引文必须逐字可核。

## 审计结果

- 审计 **108** 条：**has_rescue 68**、**no_rescue 39**、**unclear 1**。
- 关键词命中组 73 条：has 51 / no 22 —— **关键词命中里有 22/73 不是救应条款**。
- 非命中抽样组 35 条：has 17 / no 17 / unclear 1 —— **不含关键词的条目里仍有约一半确有救应条款**。

**结论：关键词筛查两个方向都不可靠**（命中组假阳 30%，非命中组假阴约 49%）。判据只能是逐条读原文。

## 对 212 条的估计（不外推为逐条结论）

总体 212 = 关键词命中 73 + 非命中 139。按各层实测比例估计各层「原文无救应条款」的条数：

- 命中层：22/73 = 30.1% → 73 条中约 22 条
- 非命中层：17/35 = 48.6% → 139 条中约 68 条

即 **212 条里约 90 条（各层 95% 区间合计约 58–120 条）原文根本没有救应条款**，
把它们记作 `unimplemented` 是把「无可实现」冒充成「待实现」。
这张估计值**只用于说明标签失真量级**，不作为逐条改标依据。

## 本批实际做了什么（只改有逐条证据的）

1. `schema.md` 与 `tools/validate-executable.py` 新增取值 **`none`**：原文没有救应条款，本条无可实现；
   `unimplemented` 收窄为「原文有救应条款、引擎尚未实现」。
2. 把**本次逐条读过的 39 条** `no_rescue` 由 `unimplemented` 改为 `none`（改标依据=下表逐条理由，不做外推）。
3. 其余 104 条**未审计**，标签一律不动——它们在按比例上很可能也混着「原文无救应」，但没有逐条证据就不改。

改标后分布：`none` 39 / `unimplemented` 173（其中 68 条本次已核实**确有**救应条款、1 条 unclear、104 条未审计）/ `self` 43 / 交叉引用 3。
