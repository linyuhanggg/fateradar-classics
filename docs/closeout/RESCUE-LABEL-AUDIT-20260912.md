# 救应标签普查：`rescue: unimplemented` 的 212 条逐条读原文定案（2026-09-12）

## 为什么普查

`references/executable/*.json` 里 258 条定义有 **212 条**标着 `rescue: "unimplemented"`（82%）。
按 `schema.md` 的字面含义，这个值读作「**原文有救应条款、引擎尚未实现**」——即一张 212 条的待实现清单。
82% 这个比例本身可疑：它更可能是把「原文根本没有救应条款」也写进了同一个值。两者混写会**虚增未决清单**。

## 方法

1. 212 条**全取**，分两波（第一波 108 条＝关键词命中组全取 73 ＋ 非命中组等距抽 35；第二波＝剩余 104 条）。
2. 每条取出该条**自己的原文**（`sources[].quote`）与 fulltext 中该段前后各 6 行的上下文，交 16 个独立校核员分批阅读（每批 13–14 条）。
3. 判据是**该条原文自己的话**，不是关键词：「制／化」出现在一般用神叙述（如「以丙火制庚金」）不算救应；
   不含这些字但语义是「出了毛病另有物可救／使其不为害／反成」的**要算**。
4. 三选一：`has_rescue`（确有救应条款，须给逐字引文）／`no_rescue`（只讲成立条件）／`unclear`。
   不确定写 `unclear`，不猜；引文须逐字可核；相邻条目的救应句不计入本条（例：QTB-M-02-01 排除属二月乙木条的「得癸透养木亦为贵」）。

## 普查结果（212/212，不是抽样估计）

- **has_rescue 105**：原文确有救应条款，逐条附逐字引文 → 这才是真正的待实现清单。
- **no_rescue 106**：原文只讲成立条件，**没有任何「出了毛病由谁来救」的条款** → 本条没有可实现的救应。
- **unclear 1**：原文残缺，无法判断。

即 **212 条里恰好一半（106 条）的 `unimplemented` 是误标**——那些条目原文根本没有救应条款，
写成「未实现」等于把「无可实现」冒充成「待实现」。

### 副产物：关键词筛查两向都不可靠

第一波的分层设计顺带量出了关键词筛查的可靠度（判据只能是读原文，不能按字面批量推断）：

- 含「救／解／制／化」的 73 条里，**22 条并非救应条款（假阳 30%）**；
- 不含这些字的抽样 35 条里，**17 条确有救应条款（假阴约 49%）**。

## 本批实际改动

1. `schema.md` 与 `tools/validate-executable.py` 新增取值 **`none`**＝原文没有救应条款（本条无可实现）；
   `unimplemented` 收窄为「原文有救应条款、引擎尚未实现」。`tools/test-validate-executable.py` 加了自测：
   `none` 不被记成依赖、非字符串仍被拒。
2. 把普查过的 **106 条 `no_rescue`** 由 `unimplemented` 改为 `none`（依据＝下表逐条理由，不外推）。
3. 其余标签不动。改标后全库：`none` 106 / `unimplemented` 106（＝105 条已核实确有救应条款 ＋ 1 条 unclear）/ `self` 43 / 交叉引用 3。

## 第二问：这 105 条「确有救应条款」的，引擎实现了吗（实测，只改有直接证据的那条）

标签普查回答的是「原文有没有救应条款」；这一问是「有条款的那些，引擎算不算」。方法与第一问不同——判据是**引擎侧**：
看该条探针实际读取的引擎出口里有没有救应判定，以及引擎里有没有对应机制。

### 已实现（1 条，已改标）

**`ZPR-E-03`「用神成败救应」`unimplemented` → `self`**。证据三条互相独立：

1. 本条**自身即救应节**，其 `satisfy_when` 明列「……干扰及**有依据的解救均已检查**，未决项为空……」；
2. 引擎有实现：`src/lib/engine/bazi/geju-execution.ts` 计算 `resolution: "有救" | "救应受损" | "无救" | "待核"`、
   `remedies`（救应之物五行）与 `explanation`，并实现 `印制伤` / `财化伤` / `印合伤` 等救应方式
   （`GejuExecutionSupport.purpose`：`以印护官或调解伤官`、`以财生官或转化伤官的作用`）；
3. 该条探针读的正是 `analysis.geju.execution.verdict` / `.route` / `.unresolved` / `…`。

**实测该机制会触发**（不是「有代码但从不产出」）：正官格 `正官见伤=无救`、印格 `七杀是否适合生印=无救`、
伤官格 `食伤与官的配合=无救`。故「未实现」与事实不符。

### `SMTH-E-13` 羊刃：`unimplemented` → `self`

救应句「**羊刃帶祿更有官印相資尤作吉論**」的四个条件全部在原文里点名、且都能判：

| 条件 | 判据（原文内） | 引擎出口 |
| --- | --- | --- |
| 羊刃在盘 | 「祿前一辰為羊刃」 | `rows[label=神煞].values` → 前提项 |
| 禄神在盘 | 「刃後一辰為祿也」 | 同上（**两读并列**，见下） |
| 官（正官或偏官） | 「官印相資」 | `tenGodsPresent(input)` → 十神 |
| 印（正印或偏印） | 「官印相資」 | 同上 |

**实测（3,060 张盘，1950–2000 每两月取样）**：`满足` 100／`信息不足` 606／`不满足` 2,354——
三种结论都出现，不是恒真也不是恒假。

**两处不替原文择一的地方（照 `liuyao-rescue.ts` 實破之日先例并列）**：
1. **「帶祿」两读**：严格读＝羊刃与禄神俱见四柱；从定义读＝「刃後一辰為祿」本段自有此句，羊刃与禄本为一体，
   不必四柱另见禄。**缺禄而官印俱见时两读结论不一致**，故引擎给 `信息不足`，并在 `undecided` 里并列两读，不择一。
2. **「又云羊刃重重又見祿富貴饒金玉」**：「重重」几重本段未界定（全书他处「重重」皆作「重复出现」但未给数目），
   故当禄神在盘时该支仍活着 → 官或印不成立时给 `信息不足` 而不是 `不满足`；禄神不在盘则该支确定不成立 → 给 `不满足`。

### `SMTH-E-08` 劫煞：**保持 `unimplemented`**（只是条件层建起来了）

救应句「**刼神包裏遇官星**主執兵權助聖明」里，引擎只能判两项：劫煞在盘、遇官星（正官／偏官）。

`包裏` 2 命中，全在本段与孤寡段）。加上「又云四位逢生」也未操作化，故：

- 引擎**即使劫煞与官星都在盘也只给 `信息不足`，永不给 `满足`**（不拿判得出的那一半冒充整句）；
- 实测（同 3,060 张盘）：`信息不足` 509／`不满足` 2,551／`满足` **0**——`0` 是设计结果，不是缺陷；

- `QTB-M-08-11`「或支成水局，癸水出干，有二戊制者」：该档案为辛日，日主占一位、月干由年干经五虎遁定死，
  三个可用天干无法同时容纳「癸出干」与「二戊（透干计）」——穷举 1950–2000 全十二时辰**无满足见证**。
  放宽成「含藏支计戊」则可成立，但**原文未界定是否含藏支**，故不替它选，**留在 `unimplemented`**。
- `QTB-M-02-04`「须要大运相扶」：救应落在**大运**，原局无从判定。

### 两处「日主自身」的过度要求（见证扫描查出，已修）

`QTB-M-04-07`「丁壬化杀」的**丁即日主**（丁日）、`QTB-M-05-10`「得戊救丙」的**戊即日主**（戊日）：
第一版规格把它们当成「另求一位」，于是要求盘上再出现一个丁／戊——**加了原文没有的条件**。
改为只求壬（另一干），两条随即取到满足见证。
