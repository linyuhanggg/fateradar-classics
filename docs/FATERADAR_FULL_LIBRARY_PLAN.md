# FateRadar 全库古籍、核心算法与 Web 联动总方案

状态：完整执行方案，尚不代表全库加工或算法建设已经完成。用户要求一次确定全量范围与验收，不再逐栏目提出局部计划。

## 交付目标与边界

交付一套从古籍段落到可计算条件、再到本盘免费解释的完整系统，并接入现有八术页面。现有资料全部纳入处理清单，现有核心算法全部纳入审查，现有主要页面栏目全部纳入内容交付。

全量处理不等于把每句话写成判断规则。目录、序跋、重复引文、案例、操作步骤、理论、无法确定的文本分别保留去向。风水、相法、择日、姓名等当前页面没有对应输入与算法的材料，进入可检索知识库及适用范围清单，不冒充已接入八术。既有明确排除的资料仍遵守其限制，不以“全量”取消边界。

当前可核对基线：catalog 55 套资料包，54 份全文文件、2 份补充 Markdown；影印来源包含普通仓库34套、Release 5套、未确认底本14套、特殊资料2套。55是资料包口径，不能称55部独立完整古籍。现有白话导出11条，其中八字3条，不等于算法规则总数。旧规则与旧客户端只能作候选与比较材料。

## 全库处理方法

原始全文与影印保持不改；工作副本统一编码、段落和章节结构。繁简、异体字只用于检索映射，不覆盖原文。页面残留、乱码、断句和缺页定位到具体段落；涉及判断方向或关键字的疑点，优先对照可用影印。没有可靠底本时保留疑点，不让模型补出的字进入引文。

为每段建立稳定ID与原文范围。书目去重区分“同书不同版”“不同书转引同段”“独立论述”，重复引文不计作多份独立支持。各段标记为理论、规则候选、案例、操作步骤、术语、序跋目录、重复或待核实，并说明去向；相关理论段落补白话，目录序跋不机械扩写成解读。

抽取分两次：先抽原文明确说出的内容，再展开实现所需但原文未明说的条件。后者必须标成解释假设，并注明理由；不得偷偷归入古籍原意。否定、例外、转折、救应和前后文作为同一审读单元，禁止截一句即生成断语。

## 规则表示与执行语义

每条规则至少包含：id、术数、主题、流派、原文段落ID、所需事实、成立条件、排除条件、位置与作用关系、干扰/救应关系、结论、白话模板、案例、审读状态。

事实使用类型化字段和稳定位置引用。八字区分年/月/日/时、天干/藏干、透藏与有效根气；其他术数分别使用宫、星、爻、课、传等位置。不得再靠一整段文字是否包含关键词判定命中。

执行结果固定分为“满足”“不满足”“信息不足”。某规则可能有救应时保留候选和未计算项；没有救应规则不等于没有救应。每个输出带实际用到的事实与失败/未知原因，允许说明为何不能下结论。

同一流派的专门条件与例外必须形成明确依赖，先检查适用范围再执行。不同流派单独给出结论及各自来源，不按书本数量投票，不强行平均成一套喜忌。无法裁决的矛盾进入分歧记录。

规则执行不能由大模型临场自由发挥。模型负责候选抽取、白话草稿和测试草稿；确定性代码负责排盘与条件判断。

所有术数沿用真实支持的输入范围审查。古籍缺少现代实现细节时，引用实际历算库或实现说明。已有算法逐项与规则库对照：有来源、实现假设、来源不符、尚未覆盖分别登记。修正错误时用能定位差异的案例说明，不能刷新golden掩盖变化。

生时反推作为明确的独立交付项：根据已知年月日与时间范围生成候选，日界附近按所选换日口径检查相邻日，不随意把每个日期扩成三天。用户事件保留时间精度、类别与不确定性。候选之间输出可比较的支持/矛盾证据及敏感条件，不宣布找回真实生辰。只有在已知时辰、预先保留事件的独立数据上评估后，才能讨论排序效果；没有标注数据时如实交付候选比较能力，不能声称准确率。它不参与首屏排盘。

## Web 一次对齐的接口

保留现有页面布局，由 Web 项目负责交互和报告呈现；本任务负责算法、事实、解释内容和导出。当前运行引擎在产品仓，修复直接落在这份权威实现，不新增一份同名运行时造成双写。古籍仓维护语料、规则定义、证据与可导出的内容；代码迁仓不是本方案的前置条件。

现有 BaziChart、各术数 points 及 reading-notes 导出继续使用。先把所需字段明确添加到实际消费的结构中，不另造无人使用的通用框架。各术数内容必须带：稳定ID、所属栏目、本盘结论、白话原因、所用事实、适用/未知条件、来源、关联盘面位置、规则与内容版本。

用户默认先看到本盘结论和解释，再展开推导及古籍原文。点柱、宫、爻或星后，使用位置ID关联内容，不通过文本搜索猜匹配。资料修改、时制切换或岁运改变后，盘面与解释基于同一份新结果同步更新，不能残留旧报告结论。

八字覆盖用户已有12个入口：命局总览、旺衰、格局、喜忌、调候、病药、专项、神煞、干支关系、大运流年、排盘资料、个人报告。其他七术按其真实页面入口形成字段映射，缺少的算法结果明确留空并解释原因，不用通用话术填满。

免费解释完全由已审读内容和确定性事实组装，不要求登录、付款或调用AI。AI追问消费同一份事实及相关依据，可用于组织回答；模型服务由产品项目配置，不能修改底层排盘事实。报告必须记录当时输入口径与所用版本，旧报告回看不伪装成新版本重算结果。

## 执行组织：全范围并行，一次总验收

按书目/术数划分互不重叠的工作包，并行进行文本处理、规则审读、算法修复和解释接入。它们是同一个完整任务的并行工作流，不是每完成一个栏目就停下来让用户重新定范围。

Grok CLI 可承担按章节抽取、白话草稿、候选条件与样例生成；每个工作包只提供必要原文和固定输出格式。Codex负责接口、条件语义、源文对照、冲突处理、算法变更与最终验收。Web任务只接收明确字段与真实样例，不收到“自行理解古籍”的模糊任务。

内部允许小提交和必要的依赖先后，避免一次巨大补丁无法定位错误；对用户按全量范围交付。模型异常时保留已完成产物，重跑失败包，不重复投喂全库。未授权新增付费服务前，不自行购买或启用收费API；已有Grok CLI按现有配置使用。

进度账本记录真实数量：资料包、有效段落、候选规则、审读结论、可执行规则、已覆盖栏目、未决项目。总规则数以完成抽取后的去重结果为准，不预造“数万条规则”目标。时间和费用按首批真实吞吐测算后更新，估算属于执行管理，不改变整体交付范围、不要求用户逐批批准。

## 总验收与完成条件

1. 全部现有资料都有处理去向；缺本、疑文、重复、非现有产品范围和明确排除项目均可定位。不能用“待处理”填满清单后宣称完成。
2. 所有对用户展示的古籍引文都能回到准确原文范围。否定与例外上下文未丢失；人工校勘、电子文本锚定和模型草稿状态分开。
3. 所有上线的主要判断都能追到输入事实、规则与解释理由；没有计算的条件不会悄悄按成立处理。
4. 所有上线的可执行规则都有针对实际判断分支的测试。成立、不成立、干扰、救应/未知分支按规则实际情况覆盖；重复测试不充数。
5. 原书可复算案例、独立已知盘与合成边界用例分开统计。模型评审、测试通过均不能自动提升人工verified或golden状态。
6. 八术主要栏目有针对当前盘面的免费解释；更换资料和选中位置时内容正确更新。网页显示与核心事实一致，无需模型服务也可使用。
7. 影响主要判断的已知错误必须修复或撤下确定性结论；不能仅加一段免责声明继续输出错结论。明确不支持的学派与能力单列，不混入完成口径。
8. 两仓通过各自必要检查，内容导出与代码版本可对应，网页项目完成集成验收；上线状态单独记录，合入main不等于已部署。

最终向用户提供可用页面、全库处理报告、规则与案例索引、源码与版本、未决争议清单。验收证明的是文本来源、计算实现和页面一致性，不是证明传统术数对现实事件的预测有效性。

## 不采用的捷径

不把全库上传向量库就称算法完成；不让模型批量改写古文后直接发布；不复制mingli旧规则当权威；不按古籍数量累加置信度；不让正文变长代替条件完整；不为了宣布全量完成编造缺失资料、准确率或人工验证。
